# Data Models & Storage Schema

## Overview

The CICS GenApp uses dual data storage:
1. **Db2 (Primary)** - Relational database for structured data
2. **VSAM (Secondary)** - Sequential file storage for performance/legacy compatibility

Both storage mechanisms maintain the same logical data model through two-phase commit coordination.

## Db2 Database Schema

### Customer Table

```sql
CREATE TABLE CUSTOMER (
    CUST_ID         DECIMAL(10,0)  PRIMARY KEY,
    CUST_NAME       VARCHAR(30)    NOT NULL,
    CUST_ADDRESS    VARCHAR(50),
    CUST_CITY       VARCHAR(20),
    CUST_STATE      VARCHAR(2),
    CUST_ZIP        VARCHAR(5),
    CUST_PHONE      VARCHAR(10),
    CUST_EMAIL      VARCHAR(40),
    CREATED_DATE    DATE,
    LAST_MODIFIED   DATE
);

KEY: CUST_ID (10-digit customer number)
```

**Field Details:**
- **CUST_ID:** Unique customer identifier (generated by sequence or named counter)
- **CUST_NAME:** Customer legal name (insurance applicant)
- **CUST_ADDRESS:** Street address
- **CUST_CITY:** City name
- **CUST_STATE:** State code (2 letters)
- **CUST_ZIP:** ZIP code (5 digits)
- **CUST_PHONE:** Telephone number (10 digits)
- **CUST_EMAIL:** Email address for correspondence
- **CREATED_DATE:** Record creation timestamp
- **LAST_MODIFIED:** Last update timestamp

**Relationships:**
- Parent to: POLICY, MOTOR_POLICY, ENDOWMENT_POLICY, HOUSE_POLICY, COMMERCIAL_POLICY
- Referential integrity required

### Generic Policy Table

```sql
CREATE TABLE POLICY (
    POLICY_ID       DECIMAL(10,0)  PRIMARY KEY,
    CUST_ID         DECIMAL(10,0)  FOREIGN KEY REFERENCES CUSTOMER,
    POLICY_TYPE     CHAR(1),       -- M/E/H/C
    COVERAGE_AMOUNT DECIMAL(12,2),
    ANNUAL_PREMIUM  DECIMAL(9,2),
    START_DATE      DATE,
    END_DATE        DATE,
    STATUS          CHAR(1)        -- A(active)/C(cancelled)
);

KEY: POLICY_ID
FOREIGN KEY: CUST_ID → CUSTOMER.CUST_ID
```

**Policy Type Codes:**
- `M` = Motor Insurance
- `E` = Endowment Insurance
- `H` = House Insurance
- `C` = Commercial Property Insurance

**Fields:**
- **POLICY_ID:** Unique policy identifier (auto-generated)
- **CUST_ID:** Foreign key to CUSTOMER table
- **POLICY_TYPE:** Single character code indicating policy type
- **COVERAGE_AMOUNT:** Total insurable value
- **ANNUAL_PREMIUM:** Premium charged annually
- **START_DATE:** Policy effective date
- **END_DATE:** Policy expiration date
- **STATUS:** A=Active, C=Cancelled

## VSAM File Storage

### KSDSCUST - Customer Records File

**File Structure:**
```
Record Key (10 bytes):     Customer ID (right-justified, zero-padded)
Record Data (variable):    Customer structure from soavcio.cpy
Record Size:               ~400 bytes average
Organization:             KSDS (Key-Sequenced Data Set)
Access Method:            VSAM
```

**VSAM Record Format (soavcio.cpy):**
```
Position    Length    Field
1-10        10        Customer ID (key)
11-40       30        Customer Name
41-90       50        Customer Address
91-110      20        City
111-112     2         State Code
113-117     5         ZIP Code
118-127     10        Phone Number
128-167     40        Email Address
168-175     8         Creation Date (YYYYMMDD)
176-183     8         Last Modified Date (YYYYMMDD)
184-400     ~217      Reserved/Extensions
```

**Access Patterns:**
- **Sequential Read:** Customer ID range queries (for reporting)
- **Random Read:** Direct lookup by Customer ID
- **Write:** Add or update customer record
- **Delete:** Logical deletion via status flag

### KSDSPOLY - Policy Records File

**File Structure:**
```
Record Key (21 bytes):  Policy Key (Policy Type + Customer ID + Policy Number)
Record Data (variable): Policy structure from soavpio.cpy
Record Size:            ~500 bytes average
Organization:           KSDS (Key-Sequenced Data Set)
Access Method:          VSAM
```

**Policy Key Composition:**
```
Position    Length    Value
1-1         1         Policy Type: M/E/H/C
2-11        10        Customer ID (right-justified)
12-21       10        Policy Number (right-justified)

Example: M0000000050000000003
         ^         ^         ^
         |         |         +-- Policy #3
         |         +---------- Customer #5
         +-------------------- Motor Insurance
```

**VSAM Record Format (soavpio.cpy):**
```
Position    Length    Field
1-21        21        Policy Key (composite key above)
22-51       30        Policy Type Description
52-63       12        Coverage Amount (999,999.99)
64-73       10        Annual Premium (99,999.99)
74-81       8         Start Date (YYYYMMDD)
82-89       8         End Date (YYYYMMDD)
90-90       1         Status (A/C)
91-120      30        Reserved for type-specific data
121-200     80        Additional policy details (flexible)
201-500     300       Extended data for future use
```

**Access Patterns:**
- **Range Scan:** All policies for customer (starts with Customer ID)
- **Random Access:** Specific policy by full key
- **Add:** New policy record creation
- **Update:** Policy modification (full rewrite)

## Two-Phase Commit Coordination

The application maintains data consistency across Db2 and VSAM through CICS two-phase commit:

```
Step 1: Begin Transaction
   EXEC CICS SYNCPOINT ROLLBACK

Step 2: Update Db2
   INSERT INTO CUSTOMER ...
   If error, rollback and exit

Step 3: Update VSAM
   VSAM WRITE to KSDSCUST
   If error, ROLLBACK affects both Db2 and VSAM

Step 4: Commit
   EXEC CICS SYNCPOINT
   Commits both databases atomically
```

**Advantages:**
- Atomic updates (all-or-nothing)
- Referential integrity maintained
- Automatic rollback on error
- No orphaned records

**Disadvantages:**
- Performance overhead (dual write)
- Complexity (maintaining two storage systems)
- VSAM not required for modern Db2-only approach

## Named Counter Server (Optional)

**Purpose:** Generate unique Customer IDs in parallel sysplex environment

**Configuration:**
```
Counter Name: GENACUSTID
Initial Value: 1000
Increment: 1
Range: 1000-9999999999
```

**Usage:**
```cobol
EXEC CICS GET COUNTER
    NAME('GENACUSTID')
    VALUE(ws-next-cust-id)
    INCR(1)
END-EXEC
```

**Alternative:** Db2 generated sequence:
```sql
CREATE SEQUENCE CUSTOMER_ID_SEQ
    START WITH 1000
    INCREMENT BY 1;

INSERT INTO CUSTOMER(CUST_ID, ...)
VALUES(NEXT VALUE FOR CUSTOMER_ID_SEQ, ...);
```

## Temporary Storage Queues

### GENACNTL - Control Queue
**Purpose:** Track customer ID allocation range

**Record Format:**
```
Queue Item 1:
  - Last Allocated Customer ID
  - Allocation Timestamp
  - Region ID (if multi-region)
```

### GENAERRS - Error Queue
**Purpose:** Log Db2 errors for monitoring

**Record Format:**
```
Queue Items:
  - Timestamp
  - Error Code
  - Error Message
  - Failed Operation
  - Associated Customer/Policy ID
```

**Monitoring:**
- TSQ browse via CICS tools
- Periodic purge of old errors
- Alert if error count threshold exceeded

## Data Integrity Constraints

| Constraint | Type | Enforcement | Description |
|-----------|------|-------------|-------------|
| CUST_ID Primary Key | Unique | Db2 | Ensures unique customer IDs |
| POLICY_ID Primary Key | Unique | Db2 | Ensures unique policy IDs |
| CUST_ID Foreign Key | Referential | Db2 | Customer must exist before policy |
| Policy Type Validation | Domain | Application | Enforced in business logic layer |
| Date Validation | Domain | Application | Start date < End date |
| Amount Validation | Domain | Application | Positive values, reasonable ranges |
| Two-Phase Commit | Atomicity | CICS/Db2 | Both storage systems update together |
