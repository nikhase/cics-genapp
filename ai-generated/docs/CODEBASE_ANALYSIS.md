## 1. Executive Summary

**Purpose**: GenApp is a demonstration general insurance application developed by IBM Hursley CICS Development team to illustrate legacy application modernization techniques and test CICS Transaction Server features on z/OS.

**Tech Stack**:
- **Language**: COBOL (Enterprise COBOL for z/OS)
- **Transaction Server**: IBM CICS Transaction Server V4.1+
- **Database**: IBM Db2 with two-phase commit
- **File System**: VSAM KSDS (Key-Sequenced Data Sets)
- **Interface**: 3270 terminal via BMS (Basic Mapping Support)
- **Build**: JCL (Job Control Language) with REXX customization
- **Optional**: z/OS Coupling Facility (named counters, shared TSQ)

**Architecture Style**: Strict three-tier architecture (Presentation → Business Logic → Data Management) with synchronous EXEC CICS LINK calls between layers.

**Health Score**: 7.5/10
- **Strengths**: Clean layered architecture, consistent naming, dual storage (Db2+VSAM), good separation of concerns
- **Concerns**: Mainframe-locked technology, tight coupling to z/OS, limited test coverage visibility, minimal error handling patterns

**Top 3 Risks**:
1. **Technology Lock-in**: Entirely dependent on IBM z/OS mainframe infrastructure (CICS, Db2, VSAM, JCL) - no portability
2. **Two-Phase Commit Complexity**: Dual write pattern (Db2 + VSAM) increases failure points and complicates rollback scenarios
3. **Limited Observability**: Error logging via TSQ (temporary storage queues) lacks structured logging, metrics, and alerting

## 3. Data & Control Flow

### Customer Add Transaction (SSC1 Option 2)

```
User enters customer data on 3270 terminal
    ↓
lgtestc1 (Presentation) validates input
    ↓ EXEC CICS LINK PROGRAM('LGACUS01') COMMAREA(32500 bytes)
lgacus01 (Business Logic) checks COMMAREA length
    ↓ EXEC CICS LINK PROGRAM('LGACDB01')
lgacdb01 (Data-Db2) generates customer number via:
    - Named counter server (EXEC CICS GET COUNTER 'GENACUSTNUM') OR
    - Db2 IDENTITY column (auto-increment)
    ↓ EXEC SQL INSERT INTO customer table
Db2 commits phase 1
    ↓ EXEC CICS LINK PROGRAM('LGACVS01')
lgacvs01 (Data-VSAM) writes customer record
    ↓ EXEC CICS WRITE FILE('KSDSCUST') RIDFLD(customer-num)
VSAM commits phase 2
    ↓ Two-phase commit completes
Return customer number via COMMAREA
    ↓ Updates GENACNTL TSQ with new high customer number
lgtestc1 displays success message with customer number
```

### Policy Inquiry Flow (SSP1-4)

- User selects policy type (Motor/Endowment/House/Commercial)
- Presentation layer (lgtestp1-4) → Business layer (lgipol01)
- Business layer → Data layer (lgipdb01) using customer # + policy # + type
- lgipdb01 executes DECLARE CURSOR for joins across policy tables
- EXEC SQL FETCH fetches matching policy with details
- Returns policy data through COMMAREA chain
- Presentation displays formatted policy on 3270 screen

### COMMAREA Structure
All inter-program communication uses a standardized COMMAREA (32,500 bytes):
- **6 bytes**: CA-REQUEST-ID (e.g., '01ACUS', '01IPOL')
- **2 bytes**: CA-RETURN-CODE (00=success, 98=length error, 80=VSAM error)
- **10 bytes**: CA-CUSTOMER-NUM
- **32,482 bytes**: CA-REQUEST-SPECIFIC (overlaid with customer/policy structures)

## 8. Technical Debt & Code Smells

### Technical Debt Items

1. **VSAM Dual Write Pattern** (7 programs)
   - **Location**: lgacdb01→lgacvs01, lgucdb01→lgucvs01, lgupdb01→lgupvs01, lgdpdb01→lgdpvs01
   - **Impact**: Acknowledged in Architecture.md as "not a best practice"
   - **Risk**: Two-phase commit failures leave system in uncertain state
   - **Effort**: HIGH - Requires data migration plan, removing 7 VSAM programs

2. **TSQ Error Logging** (lgstsq called 83 times)
   - **Location**: All programs call WRITE-ERROR-MESSAGE → lgstsq
   - **Impact**: Temporary storage queues are ephemeral, not searchable, no alerting
   - **Risk**: Errors lost on CICS restart, difficult to diagnose production issues
   - **Effort**: MEDIUM - Implement CICS event processing or external logging

3. **Hardcoded System IDs** (multiple files)
   - **Location**: JCL files with `<DB2SSID>`, `<CICSHLQ>`, `<SQLID>` placeholders
   - **Impact**: Manual customization required via REXX (cust1.rexx, mac1.rexx)
   - **Risk**: Human error during deployment, inconsistent environments
   - **Effort**: LOW - Migrate to property files or CICS variables

4. **Monolithic BMS Map** (ssmap.bms 688 lines)
   - **Location**: Single map with 5 screens (SSMAPC1, SSMAPPx)
   - **Impact**: Difficult to maintain, compile time for all screens
   - **Risk**: Change to one screen rebuilds all, testing overhead
   - **Effort**: MEDIUM - Split into 5 separate BMS maps

5. **No Automated Tests**
   - **Location**: No visible test harness, only manual test transactions (SSC1, SSP1-4)
   - **Impact**: Regression risk on changes, manual testing burden
   - **Risk**: Bugs in production, slow release cycles
   - **Effort**: HIGH - Build COBOL unit test framework or integration test suite

### Code Smells

- **Magic Numbers**: COMMAREA length 32500 hardcoded in all LINK statements
- **Long Parameter Lists**: COMMAREA overloaded with 32KB+ of data
- **Dead Code**: lgacdb02.cbl (225 LOC) appears to be alternate customer add, not referenced in main flow
- **Inconsistent Error Handling**: Mix of ABEND, return codes, and silent failures

## 9. Modernization Opportunities

### High-Priority Refactoring Candidates

#### 1. **Remove VSAM Dependency** (P0 - 6-9 months)
   - **Target**: Eliminate 7 VSAM programs (lgXXvs01), KSDSCUST, KSDSPOLY files
   - **Approach**: Db2 is already primary data source; VSAM is redundant
   - **Benefits**: Simpler two-phase commit, 30% reduction in codebase, improved reliability
   - **API Boundary**: Db2 data layer (lgXXdb01) becomes single data interface
   - **Migration Path**:
     1. Data migration: Copy VSAM → Db2 (validate customer/policy IDs match)
     2. Remove EXEC CICS LINK to lgXXvs01 from business layer
     3. Deprecate VSAM files, remove FILE definitions
   - **Risk**: Requires thorough testing of all 4 policy types (CRUD operations)

#### 2. **Extract RESTful API Layer** (P1 - 3-4 months)
   - **Target**: Expose business logic (lgXXus01, lgXXpol01) as HTTP/JSON APIs
   - **Approach**: Use CICS Web Services or z/OS Connect to wrap existing programs
   - **Benefits**: Enable web/mobile frontends, microservices integration
   - **API Boundaries**:
     - `POST /customers` → lgacus01
     - `GET /customers/{id}` → lgicus01
     - `PUT /customers/{id}` → lgucus01
     - `POST /policies` → lgapol01
     - `GET /policies/{id}` → lgipol01
     - `PUT /policies/{id}` → lgupol01
     - `DELETE /policies/{id}` → lgdpol01
   - **Service Extraction**: Business layer already well-defined with COMMAREA contracts
   - **Existing Support**: JCL jobs wsaXX01.jcl suggest web services scaffolding exists

#### 3. **Implement Event-Driven Architecture** (P2 - 4-6 months)
   - **Target**: Replace synchronous LINK with async messaging (MQ, Kafka)
   - **Approach**: CICS Event Processing with event bindings (Transaction_Counters.evbind exists)
   - **Benefits**: Decouple layers, horizontal scalability, better observability
   - **Critical Programs**: Add/Update operations (lgacus01, lgucus01, lgapol01, lgupol01)
   - **Pattern**: Command → Event → Handler
   - **Risk**: Complexity increase, eventual consistency challenges

#### 4. **Containerize Data Layer** (P2 - 6-12 months)
   - **Target**: Extract Db2 data layer as standalone service (Docker/OpenShift)
   - **Approach**: Convert lgXXdb01 programs to microservices (Java/Go/Node.js)
   - **Benefits**: Platform portability, cloud deployment, independent scaling
   - **API Contract**: Db2 SQL operations → gRPC/REST
   - **Challenges**: COBOL copybook translation, EXEC SQL migration to JDBC/ORMs
   - **Prerequisites**: Remove VSAM dependency (step 1)

## 12. Appendix

### Key Technical Characteristics

**COBOL Patterns**:
- **Version**: Enterprise COBOL for z/OS (compiler options: NODYNAM, RENT, APOST, CICS, CODEPAGE)
- **SQL Integration**: `PROCESS SQL` directive, EXEC SQL INCLUDE for copybooks
- **CICS API Style**: EXEC CICS with END-EXEC delimiters (modern syntax)
- **Error Handling**: Mix of RESP codes and ABEND (e.g., `EXEC CICS ABEND ABCODE('LGCA')`)
- **Data Structures**: Heavy use of REDEFINES for polymorphic COMMAREA

**Naming Conventions** (excellent consistency):
- **Format**: `lgX[action][type][number].cbl`
  - `X` = functional area (a=add, i=inquire, u=update, d=delete)
  - `action` = cus (customer), pol (policy), setup, stsq, stat
  - `type` = db01 (Db2), vs01 (VSAM), 01 (business logic)
  - **Examples**:
    - `lgacdb01` = "Logic Add Customer Database version 01"
    - `lgipvs01` = "Logic Inquire Policy VSAM version 01"

**Policy Type Indicators**:
- `M` = Motor insurance
- `E` = Endowment insurance
- `H` = House insurance
- `C` = Commercial property insurance

**VSAM Key Structures**:
- KSDSCUST: First 10 chars = customer number (e.g., `0000000001`)
- KSDSPOLY: First 21 chars = policy type (1) + customer ID (10) + policy number (10)
  - **Example**: `M00000000050000000003` = Motor, Customer 5, Policy 3

**Db2 Schema** (7 tables):
1. `customer` (customerNumber IDENTITY, firstName, lastName, DOB, address, phones, email)
2. `customer_secure` (customerNumber FK, customerPass, state_indicator, pass_changes)
3. `policy` (policyNumber IDENTITY, customerNumber FK, policyType, issueDate, expiryDate, brokerID, payment)
4. `endowment` (policyNumber FK, withProfits, equities, fundName, term, sumAssured, lifeAssured)
5. `house` (policyNumber FK, propertyType, bedrooms, value, address, postcode)
6. `motor` (policyNumber FK, make, model, value, regNumber, colour, cc, manufactured, premium, accidents)
7. `commercial` (policyNumber FK, address, postcode, lat/long, customer, propertyType, 4 perils with premiums, status, rejectReason)

**Build Process**:
1. `cust1.rexx` - Customize JCL with environment variables (DB2SSID, CICSHLQ, userid)

3. `@ASMMAP.jcl` - Assemble BMS maps (returns RC=4, normal for maps)
4. `@CDEF121.jcl` - Define CICS resources (group: GENALIST)
5. `@COBOL.jcl` - Compile 31 COBOL programs with CICS/Db2 precompiler
6. `@DB2CRE.jcl` - Create Db2 database, 7 tables, indexes, referential integrity
7. `@DB2BIND.jcl` - Bind Db2 plans for application
