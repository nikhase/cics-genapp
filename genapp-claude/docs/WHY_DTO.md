# Why DTOs? (Data Transfer Objects Explained)

## 🎯 What is a DTO?

A **DTO** (Data Transfer Object) is a simple object that carries data between different parts of your application - like a "data envelope" or "data container".

### Real-World Analogy

Think of it like a **postal envelope**:
- 📬 You write data on an envelope
- 📤 Send it through the mail
- 📥 Someone receives it
- 📭 They read the data off the envelope

A DTO is exactly that - it **transfers data** without any logic.

## 💡 DTO vs Entity vs Database

```
┌─────────────────────────────────────────────────────┐
│             Database Table                          │
│  (PostgreSQL - What's actually stored)              │
│  customers                                          │
│  • customer_id, first_name, last_name, etc.        │
│  • Relationships, constraints, indexes              │
└────────────────────┬────────────────────────────────┘
                     │ JPA Mapping
                     ↓
┌─────────────────────────────────────────────────────┐
│          Entity (Customer.java)                      │
│  (In-memory Java object)                            │
│  • Fields match database columns                    │
│  • Has @Entity annotation                           │
│  • Can have relationships & complex logic           │
│  • Used internally by application                   │
└────────────────────┬────────────────────────────────┘
                     │ Conversion
                     ↓
┌─────────────────────────────────────────────────────┐
│     DTO (CustomerDTO.java)                          │
│  (What we send over the network)                    │
│  • Only fields API clients need to see             │
│  • Java 21 Record (immutable)                       │
│  • Used for REST API requests/responses            │
│  • Validation annotations                           │
│  • Smaller payload (no internal fields)             │
└────────────────────┬────────────────────────────────┘
                     │ JSON Serialization
                     ↓
┌─────────────────────────────────────────────────────┐
│          JSON (Over the network)                     │
│  {"firstName": "John", "email": "john@..."}        │
│  (What the browser receives)                        │
└─────────────────────────────────────────────────────┘
```

## 📝 CustomerDTO Example

### DTO - What we send in REST API
```java
// CustomerDTO - Only public fields for API
public record CustomerDTO(
    Long customerId,
    String firstName,
    String lastName,
    String email,
    String phone,
    String address,
    String city,
    String state,
    String zipCode
) {}
```

### Entity - What's stored in database
```java
// Customer Entity - All fields, including internal ones
@Entity
public class Customer {
    @Id
    private Long customerId;

    private String firstName;
    private String lastName;
    private String email;
    private String phone;
    private String address;
    private String city;
    private String state;
    private String zipCode;

    // PLUS internal fields the API doesn't need:
    private LocalDateTime createdAt;      // ← Hidden from API
    private LocalDateTime updatedAt;      // ← Hidden from API

    // PLUS relationships:
    @OneToMany
    private List<Policy> policies;        // ← Hidden from API
}
```

**Key Difference:**
- **Entity**: All 11 fields (public + internal)
- **DTO**: Only 9 fields (public only)
- **Hidden**: createdAt, updatedAt, policies

## 🔄 Why Use DTOs?

### ❌ Without DTO (send Entity directly)

```java
@GetMapping("/{id}")
public ResponseEntity<Customer> getCustomer(@PathVariable Long id) {
    Customer customer = repository.findById(id).orElseThrow();

    return ResponseEntity.ok(customer);
    // ⚠️  PROBLEM: Returns ALL fields, including:
    //    • createdAt, updatedAt (internal details - should be hidden)
    //    • relationships (policies - causes N+1 queries!)
    //    • any sensitive data you didn't want to expose
    //
    // JSON Response:
    // {
    //   "customerId": 1,
    //   "firstName": "John",
    //   "lastName": "Doe",
    //   "email": "john@example.com",
    //   "phone": "(555) 123-4567",
    //   "address": "123 Main St",
    //   "city": "New York",
    //   "state": "NY",
    //   "zipCode": "10001",
    //   "createdAt": "2025-10-19T09:56:26.369Z",    ← Should be hidden
    //   "updatedAt": "2025-10-19T09:56:26.369Z",    ← Should be hidden
    //   "policies": [...]                            ← Could be huge!
    // }
}
```

### ✅ With DTO (send only needed fields)

```java
@GetMapping("/{id}")
public ResponseEntity<CustomerDTO> getCustomer(@PathVariable Long id) {
    Customer customer = repository.findById(id).orElseThrow();

    // Convert to DTO - only expose what's needed
    CustomerDTO dto = new CustomerDTO(
        customer.getCustomerId(),
        customer.getFirstName(),
        customer.getLastName(),
        customer.getEmail(),
        customer.getPhone(),
        customer.getAddress(),
        customer.getCity(),
        customer.getState(),
        customer.getZipCode()
        // ✅ createdAt, updatedAt, policies NOT included
    );

    return ResponseEntity.ok(dto);
    // JSON Response (clean & small):
    // {
    //   "customerId": 1,
    //   "firstName": "John",
    //   "lastName": "Doe",
    //   "email": "john@example.com",
    //   "phone": "(555) 123-4567",
    //   "address": "123 Main St",
    //   "city": "New York",
    //   "state": "NY",
    //   "zipCode": "10001"
    // }
}
```

## 🎯 Benefits of DTOs

| Aspect | Without DTO | With DTO |
|--------|------------|----------|
| **Security** | Expose internal/sensitive fields | Control exactly what you expose |
| **Performance** | Load unnecessary data + relationships | Only needed fields in response |
| **API Stability** | Entity changes break API clients | Hide internal changes from API |
| **Payload Size** | Larger JSON (5-10KB+) | Minimal payload (2-3KB) |
| **Documentation** | Unclear what fields are public | Explicit API contract |
| **Flexibility** | Limited customization | Transform/aggregate data as needed |
| **N+1 Queries** | Auto-load relationships (slow!) | No unexpected queries |
| **Versioning** | Difficult to add/remove fields | Easy API versioning |

## 🔀 Complete DTO Conversion Pattern

### Service Layer Conversions

```java
@Service
@Transactional
public class CustomerService {

    private final CustomerRepository customerRepository;

    // CREATE: DTO → Entity → Database
    public CustomerDTO createCustomer(CustomerDTO dto) {
        // 1. Convert DTO to Entity
        Customer customer = convertToEntity(dto);

        // 2. Add internal fields that DTO doesn't have
        customer.setCreatedAt(LocalDateTime.now());
        customer.setUpdatedAt(LocalDateTime.now());

        // 3. Save to database
        Customer saved = customerRepository.save(customer);

        // 4. Convert back to DTO for API response
        return convertToDTO(saved);
    }

    // READ: Database → Entity → DTO
    public CustomerDTO getCustomer(Long id) {
        Customer customer = customerRepository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException("Not found"));
        return convertToDTO(customer);
    }

    // Entity → DTO (for API response)
    private CustomerDTO convertToDTO(Customer customer) {
        return new CustomerDTO(
            customer.getCustomerId(),
            customer.getFirstName(),
            customer.getLastName(),
            customer.getEmail(),
            customer.getPhone(),
            customer.getAddress(),
            customer.getCity(),
            customer.getState(),
            customer.getZipCode()
        );
    }

    // DTO → Entity (for API request)
    private Customer convertToEntity(CustomerDTO dto) {
        Customer customer = new Customer();
        customer.setFirstName(dto.firstName());
        customer.setLastName(dto.lastName());
        customer.setEmail(dto.email());
        customer.setPhone(dto.phone());
        customer.setAddress(dto.address());
        customer.setCity(dto.city());
        customer.setState(dto.state());
        customer.setZipCode(dto.zipCode());
        return customer;
    }
}
```

## 🔍 CustomerDTO Specific Features

```java
public record CustomerDTO(
    @Null(message = "Customer ID must be null for create requests")
    Long customerId,

    @NotBlank(message = "First name is required")
    @Size(min = 1, max = 50, message = "First name must be 1-50 chars")
    String firstName,

    @NotBlank(message = "Last name is required")
    @Size(min = 1, max = 50, message = "Last name must be 1-50 chars")
    String lastName,

    @Size(max = 100, message = "Address must not exceed 100 characters")
    String address,

    @Size(max = 50, message = "City must not exceed 50 characters")
    String city,

    @Size(max = 2, message = "State must be 2 characters (e.g., CA, NY)")
    String state,

    @Pattern(regexp = "^\\d{5}(-\\d{4})?$|^$",
             message = "Invalid ZIP code format (e.g., 12345 or 12345-6789)")
    String zipCode,

    @Pattern(regexp = "^[\\d\\-\\+\\(\\)\\s]*$|^$",
             message = "Invalid phone number format")
    @Size(max = 20, message = "Phone must not exceed 20 characters")
    String phone,

    @Email(message = "Invalid email format")
    @Size(max = 100, message = "Email must not exceed 100 characters")
    String email
) {
    // Compact constructor: Normalize input data before creation
    public CustomerDTO {
        // Trim whitespace from string fields
        firstName = firstName != null ? firstName.trim() : null;
        lastName = lastName != null ? lastName.trim() : null;
        address = address != null ? address.trim() : null;
        city = city != null ? city.trim() : null;

        // Uppercase state code (e.g., "ca" → "CA")
        state = state != null ? state.trim().toUpperCase() : null;

        zipCode = zipCode != null ? zipCode.trim() : null;
        phone = phone != null ? phone.trim() : null;

        // Lowercase email (e.g., "John@EXAMPLE.COM" → "john@example.com")
        email = email != null ? email.trim().toLowerCase() : null;
    }

    // Convenience method for display
    public String fullName() {
        if (firstName != null && lastName != null) {
            return firstName + " " + lastName;
        }
        return firstName != null ? firstName : lastName;
    }
}
```

**Why Java 21 Record for DTO?**
- ✅ **Immutable**: Can't accidentally modify data
- ✅ **Auto-generates**: equals/hashCode/toString
- ✅ **Compact constructor**: Validate/normalize on creation
- ✅ **No setters**: Forces immutability
- ✅ **Less boilerplate**: No getters/setters/equals/hashCode code
- ✅ **Type-safe**: Compile-time checking
- ✅ **Perfect for DTOs**: Designed exactly for this use case

### Old COBOL Pattern
```cobol
01 LS-COMMAREA.
   05 LS-CUST-ID        PIC 9(10) VALUE ZERO.
   05 LS-FIRST-NAME     PIC X(30).
   05 LS-LAST-NAME      PIC X(30).
   05 LS-ADDRESS        PIC X(50).
   05 LS-CITY           PIC X(20).
   05 LS-STATE          PIC XX.
   05 LS-ZIP-CODE       PIC X(10).
   05 LS-PHONE          PIC X(15).
   05 LS-EMAIL          PIC X(40).
   05 LS-CREATED-AT     PIC 9(14).    ← All mixed together!
   05 LS-UPDATED-AT     PIC 9(14).    ← No separation!
   05 LS-RESERVED.
      10 LS-INTERNAL-1  PIC X(100).   ← Confusing!
      10 LS-INTERNAL-2  PIC 9(5).     ← What's internal?
   05 FILLER            PIC X(300).   ← Unused space!

32.5 KB Total Size

Problems:
❌ No separation between public/internal fields
❌ Everything in one flat structure
❌ Hard to tell what's for API vs internal
❌ Wasteful space usage
❌ No versioning support
```

### New Spring Boot Pattern
```java
// API DTO (What clients see)
public record CustomerDTO(
    Long customerId,
    String firstName,
    String lastName,
    String address,
    String city,
    String state,
    String zipCode,
    String phone,
    String email
)  // Only 9 fields, clear what's public

// Internal Entity (What we store)
@Entity
public class Customer {
    // Public fields matching DTO
    private Long customerId;
    private String firstName;
    // ... etc

    // Internal fields hidden from API
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;

    @OneToMany
    private List<Policy> policies;
}

2-3 KB JSON payload (10x smaller than COMMAREA!)

Benefits:
✅ Clear separation: public (DTO) vs internal (Entity)
✅ Only 9 fields in API
✅ Can add internal fields without affecting API
✅ Efficient JSON payload
✅ Easy versioning & deprecation
```

## 🔑 When to Use DTOs

### Use DTO When:
- ✅ Returning data from REST API
- ✅ Accepting data in REST API requests
- ✅ Hiding internal/sensitive fields
- ✅ Aggregating data from multiple entities
- ✅ Transforming entity data for specific use case
- ✅ Need validation on request data
- ✅ Different clients need different data shapes

### Don't Use DTO For:
- ❌ Internal method parameters (just use Entity)
- ❌ Repository queries (return Entity)
- ❌ Service-to-service internal calls (use Entity)

## 🎯 Key Takeaway

**A DTO is a "data envelope"** - it controls exactly what data leaves your application.

**Think of it like:**
- 📁 **Entity** = The full file in your filing cabinet
- 📋 **DTO** = The summary you're allowed to see

**Real Life Analogy:**
- 🏥 **Hospital Database** = Stores patient's full medical history (allergies, surgeries, etc.)
- 🏥 **Insurance Form** = Only shows name, address, date of birth (hides sensitive medical details)
- The DTO is like the insurance form - it shows only what's needed!
